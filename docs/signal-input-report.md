# Signal input report

Run `python3 scripts/report_signal_inputs.py` for JSON, or add `--summary` for counts. The report reads the shipped runtime catalog, current adapter bindings and attributes, the dated integration coverage and the separate MIoT inventory. It changes no runtime behavior. Pipe output to a file outside the repository if needed.

The adapter section enumerates every exact binding, its research topic, accounting classification, unit and reservoir limitations. These are software contracts; a binding is not evidence that a given SKU, firmware, robot or dock exposes it. For details and dated upstream links see [integration signal contracts](integration-signal-contracts.md). Entity availability, units, and same-reservoir association require device evidence. Conditional area/time inputs need the runtime's mop gate and applicable rate. A dose setting is not a flow measurement, and status or selected mode does not prove a physical wet phase.

Each catalog record retains model, SKU, reservoirs, sources and verification dates. Model construction is classified as capability when the catalog records it; documented nominal capacities remain specifications, not live measurements. Separately recorded owner observations identify the source and date for specific S8 wash and dock-box states, without generalizing to other installations. Each unresolved topic carries a specific reason; the unknown count is a research backlog, not a count of missing physical features. Xiaomi H50 Pro declared wash quantities are included with their action, source and limitations, not promoted to measured dose or an entity binding. Catalog capacities and `available_signals` remain separately visible with their original provenance, and are not silently promoted to verified live telemetry. Null means unknown. The inventory audit lists each extracted MIoT specification separately, including its source, revision, candidates and limitations; it is neither the runtime catalog nor proof of HA exposure or absence.

Priority gaps: no verified active wet-distance counter, measured dispensing flow, or model-specific plumbed state is established by these data. Current area/time contracts describe session statistics, not active wet distance. Washing state and settings are useful contextual inputs only under the documented adapter contracts; they do not establish measured wash volume. Complete model-specific station variants, firmware, units and source dates remain required before promoting unknowns. The report itself does not perform upstream or hardware revalidation. Existing adapter fixtures test software behavior; they do not certify hardware.

The `manual_configuration_paths` section identifies configuration-specific checks for an external physical volume counter or explicitly mapped reservoir sensors, a completed-wash counter, wet distance, and a plumbed dock. Wet distance has no implemented automatic binding. A user helper can contain an estimate rather than a physical meter. Verify the actual source, reservoir, unit and reset semantics before using any manually mapped measurement.
